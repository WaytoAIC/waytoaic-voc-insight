# VOC 洞察（基础版：退货 + 评论 ｜ 进阶版：+ Reddit）

把客户说的话，变成产品、运营、供应链、客服各自下周该干的事，并且约好哪天回来看数字变了没有。

> 课上讲的那条线：**先采集，再分析；不同来源用不同的分析方式；分析完必须变成行动；行动到期要复盘；每一环留下点东西，攒起来才是资产。**
> 这个包管的是中间两环：分析，和变成行动。
>
> **AI 不是全程都上。** 这个包里只有两件事交给 AI：一条一条读原话贴标签、写洞察。清洗、算数、画图全是脚本；判断和动作全是人。分工的规矩就一句：**脚本不编故事，AI 不算数字。**

## 什么时候不要用

- 有原话的记录不到 30 条 → 只通读，不出任何比例
- 用户只想知道一个数（"退货率多少"）→ 直接查给他，不要跑全流程
- 数据是 Reddit 讨论 → 走进阶版（见下面「进阶版：Reddit 线」）；工单、别的社媒这个包不管

## 先想清楚走哪条线

| | 退货 | 评论 |
|---|---|---|
| 谁在说话 | 买了、不满意到把钱要回去的人 | 买了、留下评价的人 |
| 问什么 | **这件事该谁改** | **哪里好、哪里不好** |
| 为什么不一样 | 退货的人几乎全在骂，分"满不满意"没意义，所以改分"该谁改"和"多严重" | 一条评论经常又夸又骂，所以夸的和骂的分开记 |
| 主图 | 平台记的原因 ↔ 读出来的真实原因（连线图） | 提得多不多 × 满不满意（散点图） |
| 这条线独有 | 原因码留剔、去平台套话、能不能挽回、两头是否对称 | 剔送测评论、标疑似刷的、按月走势、已经赢了的 |

两条线各跑各的、各算各的数。跑完之后再叠起来看，见 `references/08-两条线叠起来看.md`。

## 开跑前备好三样

| 要备什么 | 谁来弄 | 规矩 |
|---|---|---|
| **品类配置**（标签表、原因码留哪些剔哪些、两头属性、规格怎么读） | 每个品类做一次 | 标签表定了就不改。怎么从零做出来：`references/03-怎么做出自己的标签表.md` |
| **这一款的特点**（长什么样、什么料、给谁用、什么场合、为什么这么设计、可能带来什么问题） | **人填**，每一款填一次 | AI 可以从原话里列候选给人看，不许直接拿来用 |
| **这一轮要回答什么问题** | **问人** | AI 不许替他定 |

格式和例子见 `references/01-开跑前备好三样.md`。缺第二、三样就停下来问，不要用"根据原话推测"代替——最值钱的那类结论（卖点同时也是漏点）只有知道"当初为什么这么设计"才看得出来。

## 七步

### 第 0 步 · 检查数据够不够格

哪条不满足，先跟人说清楚，不硬跑。

**退货**：① 能筛出"退货"这一类，没混进"换货"（换货用的是另一套原因码）② 原因码都在配置的清单里，出现新码停下来问 ③ 客户写了字的至少 30 条 ④ 品名、规格、站点齐全 ⑤ 文件编码没坏（非英文字母在导出时变成问号是救不回来的，只能重导）⑥ 这一轮要回答什么，已问过人 ⑦ 这一款的特点，人已填

**评论**：① 有"是不是送测评论"这一列（没有的话好评率整体虚高）② 有评论全文 ③ 有星级、站点、规格、时间 ④ 规格写法统一 ⑤ **先确认拿到的是不是全量**（第三方工具常只给一部分，对一下页面上的评论总数）；有效评论：不到 30 条只读不算；50–200 条只判方向；200 条以上才做细分对比 ⑥⑦ 同上 ⑧ 有人盯着：疑似刷的、星级和文字对不上的，只标记，不自动删。脚本只抓得到两种（同一天同规格的长好评、开头几乎一样的）；**换了说法的模板好评脚本抓不到，要靠读的时候留意**，读着像一个模子出来的，在洞察里如实说。体检里报「评论来得不自然」（某个月突然暴增）时，好评的水平要打折看，按月走势不拿来下结论

### 第 1 步 · 清洗（脚本）

```bash
# 退货
python scripts/prep_return.py <导出.csv> --config 品类配置/<你的>.json --product "<产品>" \
    --out work/cleaned.csv --report work/prep.json
# 评论
python scripts/prep_review.py <导出.csv> --config 品类配置/<你的>.json --product "<产品>" \
    --out work/cleaned.csv --report work/prep.json
```

脚本跑完会打印一份**数据体检**。把它如实转述给人：剔了多少、剩多少、够不够、有什么提醒。
遇到脚本停下来（不认识的原因码、读不出的规格），**不要自己归类、不要猜**，去问人，确认后改配置。

### 第 1.5 步 · 贴标签之前，先看一眼大盘（退货）

原因码是客户在下拉框里随手选的，不准，**不能拿来判"该谁改"**。但它盖住全部退货（写了字的只是一小部分），所以当背景板用。体检里已经算好：各原因码占多少；两头属性在原因码那一层是否对称。报告里必须写明"平台预设的选项，只作参考"。

### 第 2 步 · 一条一条读，贴标签（AI）

**不要为打标写任何关键词匹配、正则或规则。** 如果你正准备写"只要句子里有某个词就……"，停下来。原话很短、高度依赖上下文，关键词会稳定地错，而且错得看不出来：

| 客户的话 | 关键词会判成 | 实际是 |
|---|---|---|
| "不漏" 和 "到处漏" | 都是"提到了漏" | 一个夸，一个骂 |
| "太大了，怪我，我已经重新下单了小一号" | 偏大 · 产品问题 | 客户自己选错 · 能挽回 |
| "我照着页面的表量的，还是小" | 偏小 · 产品问题 | 页面的事 |
| 5 星，正文写"根本没用！！" | 好评 | 差评（以文字为准） |

允许写脚本的只有两处：把打标结果写成表，和贴完之后的统计（已经有了）。

- 格子怎么填、多个值怎么分隔、方向怎么写：`references/02-打标表的格子.md`
- "该谁改"怎么判、"多严重"怎么判、拿不准怎么办：`references/04-怎么判该谁改.md`
- 一条可以贴多个标签，可以又夸又骂，都要记。好坏以文字为准，星级只拿来对照
- 没内容的格子**留空**，不要写"无""NA"
- 标签必须来自标签表。确实是新东西：这一轮先放进兜底的那一项，记成下一版的提案，**不要当场改表**

### 第 3 步 · 算数，出报告（脚本）

```bash
python scripts/build_return.py work/tagged.csv work/insights.json --config 品类配置/<你的>.json \
    --prep work/prep.json --sku <这一款的特点.json>
python scripts/build_review.py …（参数相同）
python scripts/recalc.py <输出的 xlsx>
```

先用一个只写了产品名的 `insights.json` 跑一遍，拿到 `outputs/stats.json`；**照着里面的数写洞察**，再正式跑一遍。
所有门槛跟着数据量走（进排名 = 至少 3 次、且不低于总数的 3%（退货）或 5%（评论）），不要在报告里写死任何上一款留下来的数。

### 第 4 步 · 回到原话里验证，往下再问一层

- 每个要写进报告的结论，配 2–3 条原话。配不出来的不是结论，是猜
- **只有一条的线索**不进结论，但可以写进行动清单当"待验证"，先挑验证起来最便宜的做。几条一字不差的原话可能出自同一个模板，不当几条算
- "往下再问一层"要问什么，打标时就得留好位置（配置里的"再问一层"），不能等出了结论再补
- **"没说清"的占比本身就是结论**：很多人只说"不合适"不说哪里，说明平台没给他说的地方。如实写进"这批数据答不了什么"，并变成一条"去售后里追问"的行动

### 第 5 步 · 写洞察（AI）

每次都去找这六类发现，招式见 `references/05-十二招.md`：
**已经赢了的 · 最大的那件事（拆到下一层）· 量小但严重的 · 不花钱就能改的 · 被平台字段盖住的 · 能挽回的**

三层必须走完：发生了什么 / 为什么 / 不改会怎样。第三层要指向看得见的后果，并写出"最先能看到的信号"。
固定做一项对照：这一款本来想卖给谁，实际是谁在买。格式见 `references/06-洞察怎么写.md`。

### 第 6 步 · 出行动（AI 起草，人定）

每条行动带：谁负责、依据哪几条原话、哪一档（马上止血 / 根治问题 / 防止再犯 / 要老板定）、以及**怎么才算做完——五样写全**：
看哪个数 · 现在多少 · 要到多少 · 哪天看 · **要是没变说明什么**。

写不出来，说明结论还不够具体，回第 4 步。然后导出两张表：

```bash
python scripts/export_tables.py work/tagged.csv work/insights.json --source 退货
```

AI 到此为止。认领、排时间、改状态、到期回来读那个数、写复盘结论，全是人。见 `references/07-两张表与复盘.md`。

## 进阶版：Reddit 线

基础版两条线跑顺了再做。它回答另外两个问题：**还没买的人卡在哪**、**对手的货买了之后怎么样**。
Reddit 上什么人都有、说的也不一定是你的货，所以多一步：**先分流（这人到哪一步了 × 说的是谁的货），再各用各的方法**。
怎么挑群组、怎么合规地拿、分流之后各填哪几格、出口为什么不一样：`references/09-进阶-Reddit线.md`。

## 几条不许

1. **不许用关键词代替读**（该 AI 的地方不许用机械）
2. **AI 不许算数，脚本不许编故事**（该机械的地方不许用 AI）
3. **拿不准该谁改，就判"说不清"**，不替客户猜。客户自己选错就是自己选错，不许为了让问题显得严重算成产品的
4. **不许把大筐整类处理**。"与描述不符"这类码里装着好几种责任方完全不同的事，必须逐条拆
5. **不许当场改标签表**。边打边改，前后两批就没法比了
6. **不许拿别的款的结论指导这一款**；门槛、分界线、比例一律重算
7. **两条线同表存、不混算**。不许把退货和评论加在一起算一个比例

## 交付物

| 文件 | 内容 |
|---|---|
| `<产品>_退货分诊报告.html` / `<产品>_评论洞察报告.html` | 能直接打印成 PDF。网页里不带订单号和记录编号，原话查阅留着 |
| `<产品>_退货分析.xlsx` / `<产品>_评论分析.xlsx` | 统计全部用公式连着明细，业务自己改一个标签，数字跟着变 |
| `两张表/表一-原话和打标-*.csv`、`表二-行动-*.csv` | 导进飞书多维表格用 |
| `跨款汇总表.csv`（`fingerprint.py`）| 每跑一轮接一行，跑过四五款之后用来看"是这一款的事还是整条线的事" |

## 运行环境

| 环节 | 有文件交付工具时 | 纯命令行 |
|---|---|---|
| 输出目录 | `/mnt/user-data/outputs`（脚本自动识别） | `./outputs` |
| 公式重算 | `recalc.py` 调环境自带的重算器 | 调本机 LibreOffice；都没有就打印说明，不阻断 |
| 交付 | 用文件交付工具，Excel 在前 | 打印绝对路径，并说明 Excel 要用表格软件打开才会算出统计页 |

判断和计算可以拆给两个 agent：一个读原话、写 `tagged.csv` 和 `insights.json`；另一个只跑脚本。交接界面就这两个文件。

## 一次完整运行的检查清单

- [ ] 第 0 步逐条确认；这一轮要回答什么已问过人；这一款的特点人已填
- [ ] 数据体检已如实转述（剔了多少、够不够、有什么提醒）
- [ ] 逐条读着打的标——确认没有为打标写过任何关键词或规则
- [ ] 大筐里的原话已逐条拆开
- [ ] 洞察里的每个数都来自 `stats.json`，没有一个是凭印象写的
- [ ] 每个结论都有原话；只有一条的线索写成了"待验证"
- [ ] 三层洞察走完，第三层写了"最先能看到的信号"
- [ ] 六类发现都找过一遍（找不到的如实说没有）
- [ ] 每条行动五样写全，并挂上了依据的原话编号
- [ ] "这批数据答不了什么"写了真话（没说清的占比、样本薄的分组、只有一条的线索、工具自己的毛病）
- [ ] 已跑 `recalc.py`、`export_tables.py`、`fingerprint.py`
