# 开跑前备好三样

## 一、品类配置（每个品类做一次）

一个 JSON 文件，放在 `品类配置/`。所有跟品类有关的东西都在这里，脚本里一个字都不写死。
对照 `品类配置/示例-AI眼镜配件.json` 改。里面有这几块：

| 哪一块 | 是什么 | 怎么来 |
|---|---|---|
| `输入列` | 你导出的表格里，列名叫什么 | 照着你的导出文件填右边 |
| `原因码` | 哪些退货原因码留下、哪些剔掉、哪些是"大筐" | 见下面"原因码怎么分" |
| `平台套话` | 退货原话开头的下拉选项、结尾的"是否愿意被联系" | 翻 20 条原话就能列出来 |
| `两头属性` + `对称档位` | 两头都可能错的属性（大小、高矮、松紧……）和判定线 | 判定线**每个品类自己标，不能沿用别的品类** |
| `规格解析` | 从规格里能自动读出哪些属性 | 只放能稳定读出来的；读不出就让脚本停 |
| `哪件事` | **标签表**：大类 → 细项；哪些细项有两头；哪些细项要往下再问一层 | `03-怎么做出自己的标签表.md` |
| `谁在说` / `什么情况下` / `过程感受` | 另外三类标签的取值 | 同上，跟标签表一起做 |
| `该谁改` | 四个筐 + 说不清 + 其他，各自归哪个部门 | 四个筐不用改，部门名改成你们公司的 |
| `图上文字` | 报告上跟品类有关的那几句话 | 改成你的品类的说法 |

### 原因码怎么分

- **留**：跟产品体验有关的（与描述不符、有缺陷、质量不满意、不兼容、买错了……；分大小号的品类还有"太大""太小"）
- **剔**：物流的事、客户改主意、没给原因
- **大筐**：里面装着好几种完全不同的事的码（几乎一定包括"与描述不符"）。这类必须逐条读原话拆开

清单不是亚马逊的全集，只是你这份数据里出现过的。脚本遇到清单外的码会**停下来**——去问负责人，确认后加进配置，版本号加一。

### 两头属性怎么找

问一句：**这个属性，客户会不会既嫌多、又嫌少？** 会，就是两头属性。鞋的大小、鼻托的高矮、床垫的软硬、灯的亮暗、咖啡的浓淡都是。
两头都有人抱怨是常态。要看的不是量，是两头差多少，见 `05-十二招.md` 第 1 招。

## 二、这一款的特点（人填，每一款填一次）

```json
{
  "产品": "和数据里「产品」那一列一致",
  "这轮要回答什么": "一句话",
  "这一款的特点": [
    {"长什么样": "", "什么料": "", "给谁用": "", "什么场合用": "",
     "为什么这么设计": "", "可能带来什么问题": ""}
  ],
  "这一款特有的标签": ["只有这一款才有的结构上的标签，写在这里，不进公共标签表"]
}
```

填 3–5 项，只填这一款独有的。例子见 `samples/AI眼镜配件/这一款的特点.json`。

**为什么必须人填**：AI 只能从原话里看到客户提了什么，看不到产品当初是怎么设计的、为什么这么设计。
而最值钱的一类结论——"卖点同时也是漏点"——恰恰依赖这个。例：垫片有意做宽一圈是为了好贴，客户看到的是胶边外露。
不知道"有意做宽"，就只会得出"做工不好"这种没用的结论。

允许：让 AI 从原话里把高频提到的设计相关说法列成候选，给人看。
不允许：把候选直接当产品特点用。客户提到某个词，不代表那是实际设计，更不代表你知道设计意图。

拿不到的信息（比如大货批次号），不要假装这个缺口不存在，也不要用推测填补。写进"这批数据答不了什么"。

## 三、这一轮要回答什么

必须问人，AI 不许替他定。上一轮的问题换一款就不成立了。常见的问法：

- 退货里哪些该改产品、哪些该改页面、哪些能挽回
- 下一批货先改什么、优先级怎么排
- 某个卖点到底是加分项还是减分项
