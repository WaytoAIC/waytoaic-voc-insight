# 洞察怎么写（insights.json）

**脚本不编故事，AI 不算数字。** 所有数字由脚本从打标表里算出来，放在 `outputs/stats.json`。
你在 `insights.json` 里只写叙述：论点、因果、判断、行动。要写数字，只能写 `stats.json` 里已经有的。

做法：先放一个只有 `{"product": "…"}` 的 insights 跑一遍脚本，拿到 `stats.json`；照着它写；再正式跑一遍。

## 两条线共用的部分

```jsonc
{
  "product": "和数据里「产品」一致",
  "headline": "论点，不是题目。可以用 <em> 标出一段",
  "subtitle": "数据范围 + 这一轮要回答什么",

  "layers": [                       // 三层，必须三条都有
    {"level": "描述性", "q": "发生了什么", "title": "…", "body": "…"},
    {"level": "诊断性", "q": "为什么发生", "title": "…", "body": "…"},
    {"level": "预测性", "q": "不改会怎样", "title": "…", "body": "… 最先能看到的信号：…"}
  ],

  "todo": [                         // 行动清单，一条一个对象
    {"id": "A1",
     "tier": "马上止血",             // 马上止血 / 根治问题 / 防止再犯 / 要老板定
     "attr": "页面的事",             // 该谁改
     "owner": "运营 · 页面",
     "problem": "一句话说清是什么问题",
     "body": "做什么、为什么",
     "metric": "看哪个数", "now": "现在多少", "target": "要到多少", "when": "哪天看",
     "if_not": "要是没变，说明什么、下一步转去做什么",
     "refs": [1, 10, 12]}          // 依据的原话序号。"依据多少条"由脚本去数，你不要填数字
  ],

  "caveats": ["这批数据答不了什么，逐条写"],
  "sig": "页脚落款"
}
```

## 退货线多出来的

```jsonc
{
  "eyebrow": "页眉小字",
  "scope_lede": "漏斗那一节的导语：多少笔 → 剔掉多少 → 多少条有原话；分母是哪个数",
  "sym_lede": "两头是否对称那一节的导语",
  "sankey_lede": "连线图的导语：哪个大筐里装了几种不同的事",
  "triage_lede": "该谁改那一节的导语",
  "pain_note": "客户在说什么那一节的注",
  "sections": [                     // 分章节，每个主要发现一节
    {"eyebrow": "这一节属于六类发现里的哪一类",
     "title": "论点", "lede": "…",
     "bars": [["名字", 9], ["名字", 5]],                       // 可选，横条
     "quotes": [{"tag": "短标签", "attr": "产品的事",            // 可选，原话墙
                 "text": "原话", "cite": "规格 · 平台原因"}],
     "body": "解读，可以用 <b>"}
  ]
}
```

## 评论线多出来的

```jsonc
{
  "thesis": ["黑底块里的论点，一行一句，不超过 4 行"],
  "lead": "论点之后的一段展开",
  "trend_note": "按月走势怎么读",
  "cross_note": "分组里最值得说的一格",
  "sym_note": "逐项看两头怎么读",
  "pain_note": "差评最多的事那张表的导语",
  "drill": {"title": "…", "body": "往下再问一层的发现，含'没说'的占比",
            "quotes": [{"text": "原话", "cite": "星级 · 规格 · 月份"}]},
  "chains": [                       // 因果链，2–4 条
    {"tag": "批次链", "title": "一句话结论", "body": "因果解释"}
  ],
  "opportunities": [{"title": "一、…", "body": "…", "quotes": [...]}],
  "quotes": [{"conclusion": "结论", "text": "原话", "idx": 12, "star": 2}],   // 进 Excel 的「结论对原话」
  "tier_when": {"马上止血": "当周能动", "根治问题": "按月算"}
}
```

## 写法上的规矩

**标题写论点，不写题目。** "某款退货分析"是题目；"高度没做偏，做偏的是宽度"是论点。
图的形状往往直接给出论点：提得多的集中在不满意那一侧，这本身就是一句话结论。

**因果链的名字要说出类型**：结构、批次、规格、预期、供应、售后……不要叫"问题一二三"。编号不带信息，类型带。

**三层必须走完。** 停在第一层的是数据报告，不是洞察。第三层要指向看得见的后果（退货率、星级、某个规格的客户流失），
并写出"最先能看到的信号"——改完之后哪个数应该先动、要是没动说明什么。不要写"体验会变差"。

**固定做一项对照**：这一款本来想卖给谁（人填的那张表），实际是谁在买（打标得出来的）。
实际的人比设计的宽 → 新场景的机会；实际的人跑偏了 → 流量或页面把货卖给了错的人，这是上游原因，比改产品更该先动；
设计的场景没人提 → 这个卖点没被感知到。

**每个章节只放一个发现。** 不要把所有内容堆在一节里，也不要为了凑数把只有一两条支撑的发现单列成节。

**"这批数据答不了什么"要写真话。** 见 `05-十二招.md` 第 11 招。
